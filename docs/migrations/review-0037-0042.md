# Review of migrations 0037-0042

For the owner to read before anything is applied anywhere. **None of these
migrations has been applied to any real database, and no real (production) database was looked
at.** They were run on throwaway local databases only: PostgreSQL 16 with a Supabase stub, and
a local stack made from Supabase's own Postgres 15.8 image with GoTrue and PostgREST (see
"Evidence"). Branch `ccr-29322d12-v8wkmd`. **Tested commit: `d04e2e9`** (the results below are for
that commit; later commits only change documents).

## At a glance

## What each one does

### 0037: a renamed word keeps its place

*Before:* an admin renames a word. Players' progress follows (migration 0017), but
the library tables key the word by its old text. The next sync flagged the old sense deleted
and made a new one, so every library entry and view that held the word was left on a
deleted word.

*Now:* `dictionary_sync()` calls `dictionary_follow_renames()` first. For each word alias
(old -> new) it renames the sense in place when the new name is in the content, the old
name is not, and no sense has the new name yet. The sense keeps its id, so library entries,
views and sharing keep working.

- **Data:** updates `senses.legacy_key`, `rev`, `updated_at` of renamed words, inside the sync.
- **Permissions:** `dictionary_follow_renames()` is revoked from everyone but its owner; it is
  only called from `dictionary_sync()` (admin only, unchanged grants).
- **Not repaired:** renames made **before** this migration left entries on deleted senses.
  The migration does not heal them. Find them with:

  ```sql
  select e.user_id, e.sense_id, s.legacy_key as old_key, a.to_key as new_key
  from public.library_entries e
  join public.senses s on s.id = e.sense_id and s.deleted_at is not null
  join public.item_key_aliases a on a.kind = 'word' and a.from_key = s.legacy_key
  where e.removed_at is null;
  ```
  A repair (move the entries and view items to the new sense) is a separate piece of work.

### 0038: deleting a player who used the library

*Before:* `admin_delete_player` stopped with a foreign-key error for any player who had a
view, a word of their own, a share, a link or a catalog entry (the library tables do not
cascade). Nothing was deleted.

*Now:* the function removes the player's catalog entries and takes, links, shares, view contents, views,
own words and their links first, then the account. Copies other players took stay theirs.

- **Data:** only for the player being deleted. The audit line is written as before.
- **Permissions:** unchanged (admin only; a player is refused).

### 0039: no rename into an existing name

*Before:* renaming A to B when B existed "merged" the two words' progress and left library
entries on a deleted word.

*Now:* `content_save_v2` checks the renames before writing anything. A word is identified by
its text without case and with spaces collapsed (the app's `renameProblem` uses the same rule).
If another live word has the new name, the save fails with `23505`: *There is already a word
called "B". Choose another name, or edit that word.* Nothing is written. Allowed: a change of
case or spacing of the word's own name; another meaning of the same headword (`Cast`,
`Cast (to throw)` are two words); a rename sent again after its answer was lost (its alias
exists); renames of categories (unchanged).

- **Data:** none. **Permissions:** unchanged (admin only).
- `apply_item_renames()` (the low-level step) was found to be a way around this check; see 0041.
- Merging two words is not part of this; it needs its own feature with a preview.

### 0040: an offered view ends with the friendship

*Before:* after a friendship ended, the offer stayed in the inbox and the badge and failed on
accept; if the friendship came back, the old offer was back too.

*Now:* `friend_remove` ends the waiting offers between the two (both directions);
`view_shares_inbox` lists only offers between current friends and ends stale ones on sight (it
is now `volatile` because of that write); the accept still checks the friendship; accepted
copies stay; dismissed/accepted offers are not touched; the sender can offer again.
`collection_shares.status` accepts the new value `expired`. The app's badge counts the inbox, so
it follows.

- **Data, one time:** `update collection_shares set status = 'expired' where status = 'pending' and not are_friends(...)`.
  On the made-up data of the upgrade check: 1 of 2 waiting offers.
- **Locks:** `alter table ... drop/add constraint` takes an exclusive lock on `collection_shares`
  for a moment (the table is small: one row per offer).
- **Permissions:** unchanged grants; `view_shares_inbox` and `friend_remove` stay `authenticated` only.

### 0041: the rename step is not an API

*Found by a test (red first):* `apply_item_renames` was granted to `authenticated` (0017). It refuses
non-admins, but an admin could call it **directly** with any list of renames: it then moved or merged
every player's progress (keeping the record with more answers) with no content change and without the
check of 0039. *Now:* nobody but its owner can execute it; `content_save_v2` (security definer, same
owner) still calls it. The app never called it directly. A client that did would get `42501`.
Checked: the privileges (`has_function_privilege`) for `anon`/`authenticated`; a direct call as admin, player
and visitor is refused (`42501`), also through PostgREST; a content save with a rename still works.

### 0042: one progress save is applied once

*The defect (red test first):* progress is saved as whole sections, and the client merges two devices by
adding what each changed since its own base. If a save reached the database but its answer was lost, the
device sent it again; if another device had saved in between, the second delivery was added on top of a
result that already held it: **100 -> 150 (lost answer), another device 100 -> 130 (merged to 180), resend
gave 230, not 180**, with the leaderboard score and this week's points counted twice.

*Now:* every logical save carries an id (`p_op`). The database stores the id with the revisions it produced
(`progress_ops`, key (user, id)) in the same transaction, under the player's existing advisory lock; the
same id again answers `{duplicate: true, revs}` and changes nothing. So check, write and record are
atomic, and two deliveries at the same moment give one application (tested with concurrent calls).
A save refused for a stale revision, or failed, records nothing and its id can be sent again. The same id
with different content is an error (`22023`). Records older than 90 days are deleted when the player saves.
The table has RLS on and no policy; no privilege for `anon` or `authenticated`.

*The client:* keeps the id of an unanswered save until it is answered, **also across a closed page** (it is in the
IndexedDB snapshot), and asks about it again first, before sending anything newer or merging. If the
database says "already applied", that save becomes the base for the next merge (so nothing is added twice);
if it was refused as stale it was never applied and the normal merge runs. A new state never reuses an id.
An error with a database code (SQLSTATE or `PGRST…`) means "rolled back, not applied" and frees the newest
state at once; an error without a code ("Failed to fetch") means "unknown" and keeps the id.
**Behaviour change to know:** while a save has no answer, the retry (every 15 s) is that same save, and the newest
state follows after it is answered (before, the retry sent the newest state directly).

*Old and new clients:*

| Client | Database | Result |
| --- | --- | --- |
| old (no `p_op`) | with 0042 | works as before: `p_op` defaults to null, no record, **no protection** (an old client can still double count) |
| new | with 0042 | protected |
| new | without 0042 | PostgREST answers `PGRST202` (404) to the unknown argument; the client sends the save again without an id and stops sending ids. Works as before, without protection. Tested against real PostgREST with the migrations rolled back |
| old | without 0042 | as before |

The old six-argument function is **dropped** (two overloads would be ambiguous for named arguments); a call
with the six arguments goes to the new function through the default (tested through PostgREST).
Limits, stated plainly: protection exists only for a client that sends ids; an operation older than 90 days is
forgotten; two tabs of one browser profile share one snapshot (not changed); a client that wipes its storage
loses its pending id (the save may then be applied twice, as before this change).

## If something goes wrong

1. **Back up first** (before applying): a database dump or point-in-time recovery point. At least
   `collection_shares`, `senses`, `item_key_aliases`.
2. **The app misbehaves after deploying it:** redeploy the previous build. The database stays as it is
   (compatible, shown above).
3. **The database misbehaves:** run the rollback script in one transaction:
   `psql "$URL" -1 -f supabase/rollback/0037_0042_down.sql`. It puts the replaced functions back as
   they were (generated from a database at migration 0036), gives `apply_item_renames` its grant back, drops
   `progress_ops` and the new `save_progress_v2`, drops the two helpers, turns `expired` offers
   into `dismissed` (not back to waiting: many were between players who are not friends) and restores the old
   status check. After running it on the check database, **the whole schema is identical to before** (710
   objects: functions with source hash and who may execute them, tables with RLS and privileges, columns,
   constraints, indexes, policies, triggers), and the migrations applied again give the same schema as the first time.
4. **What rollback cannot undo:** the table of operation ids (a client that still holds an unanswered save would then apply it again); senses already renamed in place keep the new key (right anyway); players already
   deleted stay deleted; ended offers do not come back as waiting.
5. After either, ask PostgREST to reload its schema (`notify pgrst, 'reload schema'`; the migrations and the
   rollback do it).

## Before applying or rolling back anywhere real: compare, do not assume

The upgrade and rollback assumptions are about a database in the state "migrations 0001-0036 as in this
repository". A real project may differ (a change made by hand, a migration applied in another way). The local
definitions are not evidence about it. Run, against the real database, **read-only** (it sends only SELECTs in a
read-only session):

```
supabase/ci/preflight-compare.sh "postgres://…"
```

It prints the platform's list of applied migrations when it can, then compares the objects these migrations touch
(function source hashes and who may execute them, the `collection_shares` table and its constraint, the new
table) with the committed fingerprints in `supabase/ci/expected/`. Verdict `BEFORE` = the migrations can be
applied; `AFTER` = they are applied as here and the rollback fits; `OTHER` = stop, each printed line must be
explained first. **It has not been run against any real database** (none was available or touched). It was run
on the local databases: `BEFORE` after 0036, `AFTER` after 0042, `BEFORE` again after the rollback, `OTHER` (with
the line) after a privilege was removed by hand.
