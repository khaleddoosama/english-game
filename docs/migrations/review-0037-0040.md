# Review of migrations 0037-0040

For the owner to read before anything is applied anywhere. **None of these
migrations has been applied to any real database.** They were run only on
throwaway local PostgreSQL 16 databases (see "Evidence"). Branch
`ccr-29322d12-v8wkmd`.

## At a glance

| # | File | Changes | Data touched | Reversible |
| --- | --- | --- | --- | --- |
| 0037 | `0037_rename_keeps_sense.sql` | `dictionary_sync()` first moves a renamed word's sense to its new name; new internal `dictionary_follow_renames()` | `senses.legacy_key` of renamed words, only when the sync runs | functions yes; the keys stay (they are the right ones) |

Order: **0037, 0038, 0039, 0040**, each in its own transaction (the repository's
`supabase/ci/*.sh` apply them with `psql -1`). They do not depend on each other; they
replace different functions (0037 `dictionary_sync`, 0038 `admin_delete_player`,
0039 `content_save_v2`, 0040 `friend_remove` and `view_shares_inbox`).

## What each one does

### 0037: a renamed word keeps its place

*Before:* an admin renames a word. Players' progress follows (migration 0017), but
the library tables key the word by its old text. The next sync flagged the old sense deleted
and made a new one, so every library entry and view that held the word was left on a
deleted word.

*Now:* `dictionary_sync()` calls `dictionary_follow_renames()` first. For each word alias
(old -> new) it renames the sense in place when the new name is in the content, the old
name is not, and no sense has the new name yet. The sense keeps its id, so library entries,
views and sharing keep working.

- **Data:** updates `senses.legacy_key`, `rev`, `updated_at` of renamed words, inside the sync.
- **Permissions:** `dictionary_follow_renames()` is revoked from everyone but its owner; it is
  only called from `dictionary_sync()` (admin only, unchanged grants).
- **Not repaired:** renames made **before** this migration left entries on deleted senses.
  The migration does not heal them. Find them with:

  ```sql
  select e.user_id, e.sense_id, s.legacy_key as old_key, a.to_key as new_key
  from public.library_entries e
  join public.senses s on s.id = e.sense_id and s.deleted_at is not null
  join public.item_key_aliases a on a.kind = 'word' and a.from_key = s.legacy_key
  where e.removed_at is null;
  ```
  A repair (move the entries and view items to the new sense) is a separate piece of work.

### 0038: deleting a player who used the library

*Before:* `admin_delete_player` stopped with a foreign-key error for any player who had a
view, a word of their own, a share, a link or a catalog entry (the library tables do not
cascade). Nothing was deleted.

*Now:* the function removes the player's catalog entries and takes, links, shares, view contents, views,
own words and their links first, then the account. Copies other players took stay theirs.

- **Data:** only for the player being deleted. The audit line is written as before.
- **Permissions:** unchanged (admin only; a player is refused).

### 0039: no rename into an existing name

*Before:* renaming A to B when B existed "merged" the two words' progress and left library
entries on a deleted word.

*Now:* `content_save_v2` checks the renames before writing anything. A word is identified by
its text without case and with spaces collapsed (the app's `renameProblem` uses the same rule).
If another live word has the new name, the save fails with `23505`: *There is already a word
called "B". Choose another name, or edit that word.* Nothing is written. Allowed: a change of
case or spacing of the word's own name; another meaning of the same headword (`Cast`,
`Cast (to throw)` are two words); a rename sent again after its answer was lost (its alias
exists); renames of categories (unchanged).

- **Data:** none. **Permissions:** unchanged (admin only).
- `apply_item_renames()` (the low-level step, admin only) is unchanged: called alone it still
  moves progress without this check.
- Merging two words is not part of this; it needs its own feature with a preview.

### 0040: an offered view ends with the friendship

*Before:* after a friendship ended, the offer stayed in the inbox and the badge and failed on
accept; if the friendship came back, the old offer was back too.

*Now:* `friend_remove` ends the waiting offers between the two (both directions);
`view_shares_inbox` lists only offers between current friends and ends stale ones on sight (it
is now `volatile` because of that write); the accept still checks the friendship; accepted
copies stay; dismissed/accepted offers are not touched; the sender can offer again.
`collection_shares.status` accepts the new value `expired`. The app's badge counts the inbox, so
it follows.

- **Data, one time:** `update collection_shares set status = 'expired' where status = 'pending' and not are_friends(...)`.
  On the made-up data of the upgrade check: 1 of 2 waiting offers.
- **Locks:** `alter table ... drop/add constraint` takes an exclusive lock on `collection_shares`
  for a moment (the table is small: one row per offer).
- **Permissions:** unchanged grants; `view_shares_inbox` and `friend_remove` stay `authenticated` only.

So the order between app and database does not matter for correctness. Recommended: apply
the migrations first (they are compatible with the running app), then deploy the app.

What the previous app shows with the new database: a rename into an existing name by an
admin gives the server's message as an error (it had no check of its own); the inbox has the
same shape; it never reads the `expired` status.

## If something goes wrong

1. **Back up first** (before applying): a database dump or point-in-time recovery point. At least
   `collection_shares`, `senses`, `item_key_aliases`.
2. **The app misbehaves after deploying it:** redeploy the previous build. The database stays as it is
   (compatible, shown above).
3. **The database misbehaves:** run the rollback script in one transaction:
   `psql "$URL" -1 -f supabase/rollback/0037_0040_down.sql`. It puts the five replaced functions back as
   they were (generated from a database at migration 0036), drops the two helpers, turns `expired` offers
   into `dismissed` (not back to waiting: many were between players who are not friends) and restores the old
   status check. It was run after the upgrade on the check database, and the five functions were identical to
   before.
4. **What rollback cannot undo:** senses already renamed in place keep the new key (right anyway); players already
   deleted stay deleted; ended offers do not come back as waiting.
5. After either, ask PostgREST to reload its schema (`notify pgrst, 'reload schema'`; the migrations and the
   rollback do it).
