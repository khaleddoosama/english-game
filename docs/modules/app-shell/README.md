# Module: app-shell

Start-up, routing, global layout, player preferences, and the wiring between modules. Today most of the wiring is one large component. Proposed boundary, see [module-map.md](../../architecture/module-map.md). Decision: [ADR 0009](../../adr/0009-history-api-router.md).

## 1. Purpose and scope

**Purpose.** Turn the address into a screen, load what the game needs, hold the app-wide state, and connect screens to the modules that do the work.

**Responsibilities (Implemented)**

- Bootstrapping: [main.jsx](../../../src/main.jsx), [App.jsx](../../../src/app/App.jsx), loading app settings, creating the repo, cleaning up on sign-out.
- [WordHunter.jsx](../../../src/app/WordHunter.jsx): loads content and progress, owns most game state, chooses the screen, runs the save effects, handles sign-out, import and export wiring, admin content operations, session handlers (see [practice](../practice/README.md)).
- Routing: [router.js](../../../src/lib/router.js).
- Layout pieces: [Shell.jsx](../../../src/features/shell/Shell.jsx) (bottom navigation, save status, skeleton), [ConfirmDialogs.jsx](../../../src/features/shell/ConfirmDialogs.jsx).
- App-wide settings (admin controlled): [appSettings.js](../../../src/lib/appSettings.js).
- Player preferences screen: [SettingsPage.jsx](../../../src/features/settings/SettingsPage.jsx); the values are normalised by `normalizeSettings` in the engine and saved with progress.

**Out of scope.** Game rules ([learning-engine](../learning-engine/README.md)), persistence ([content](../content/README.md), [progress](../progress/README.md)), feature screens.

## 3. Files, screens and database objects

- Routes and screens are listed in [current-state.md](../../architecture/current-state.md#3-screens-and-routes).
- Tables: `app_settings` (read for everyone including signed-out visitors; written by the admin only).
- Functions: `app_setting(key)`, `admin_save_settings(data)`.
- Browser storage: localStorage `wh-app-settings` (cached settings), `wh-admin-path`, announcement-hidden flag.
- Service worker and manifest: generated by `vite-plugin-pwa` ([vite.config.js](../../../vite.config.js)); unknown non-API paths fall back to `index.html`.

## 4. Business rules and permissions

- Route guards (in WordHunter): unknown path, `/admin` for non-admins, `/play` with nothing to play, and `/leaderboard` when ranks are off all redirect home. They are display rules. The database enforces access.
- Maintenance mode: players see a waiting screen with the admin's message; the admin plays on. This is a browser check only (`PE-03`).
- Announcement: shown on Home until the player hides it (remembered per announcement text).
- Bottom navigation hides during a session, the final report, the speed round and the admin panel. The Ranks tab is hidden when ranks are off; the Admin tab appears for admins.
- Player preferences are clamped to allowed values (round length 4 to 30, new words 0 to 10, weak review size 3 to 20, daily goal 5 to 100, Speed Round seconds from a fixed list, text size, shortcuts, reduced motion, defaults for Live). A new player starts from the admin's defaults.

## 5. Data flow

1. `loadAppSettings()` runs when the module loads; the cached copy is used meanwhile and when offline. It is **not** refreshed while the app stays open.
2. After sign-in `WordHunter` loads content and progress together. On success it applies them and starts the effects; on failure it shows the error screen with a retry button and does not start from empty data.
3. Effects: progress save (debounced 600 ms), content save (admin only, 150 ms), other-device refresh on focus or when the tab becomes visible (at most every 10 seconds), a library inbox check on each screen change.
4. Navigation changes the URL; the screen is derived from the URL, so a refresh keeps the place.

## 6. Failure, retry, cancel, offline

- Load failure: error screen, "Try again" reloads the page. Saved progress is not touched.
- Offline start: cached content, a progress snapshot, the cached profile and settings let the game open. The header shows offline.
- Page hide or close: pending debounced saves run at once. An admin's content write in flight asks for confirmation before leaving.
- Leaving a screen cancels AI jobs started from it (see [ai-media](../ai-media/README.md)).
- Because settings are loaded once, a maintenance switch takes effect for an open tab only after it reloads.
- Storage: a warning banner appears when a content save or a progress reset fails. When the browser refuses to keep the local progress copy, the save status turns to error and the console explains it.

## 8. Example journey

A player has the game open on a phone, switches to another app for ten minutes, then returns.

1. On hide, pending saves run at once; the header shows saving then saved.
2. On return (the tab becomes visible, at most every 10 seconds) `repo.refreshProgress()` asks the server whether another device changed progress. If the player also played on a laptop, the two are merged and the screens update. No notice is shown (a "merge" toast style exists, but nothing sets it).
3. If the admin switched maintenance on meanwhile, nothing changes until the tab reloads.
